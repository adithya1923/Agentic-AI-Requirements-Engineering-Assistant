# Phase 2 — Application Foundation

## 1. Objective

Create a small, working frontend/API/database foundation for the **Agentic AI Requirements Engineering Assistant for Trade Finance and Letters of Credit**, consistent with the approved scope in [Phase 1](phase-1-use-case-definition.md). The application manages project records only. It does not perform LC operations or implement later-phase AI functions.

## 2. Architecture

```text
Browser: React + Vite, 127.0.0.1:5173
             │ JSON over HTTP
             ▼
Node.js + Express API, localhost:4000
             │ pg connection pool
             ▼
PostgreSQL 16, Docker Compose, localhost:5432
```

The browser calls the API for health and project data. Express validates requests and returns structured JSON errors. PostgreSQL is the persistence layer; project pages do not use static mock project records.

## 3. Technology Choices

| Layer | Choice | Reason |
|---|---|---|
| Frontend | React 18, Vite 5, JavaScript, React Router 6 | Small SPA with straightforward local development and navigation |
| Backend | Node.js ES modules, Express 4 | Minimal HTTP API framework matching the requested stack |
| Database access | `pg` connection pool | Direct PostgreSQL-compatible parameterized queries without an extra ORM layer |
| Configuration | `dotenv` and environment variables | Local configuration without committing credentials |
| Local database | PostgreSQL 16 Alpine image via Compose | Reproducible local database with named persistent volume |

No AI, agent, embedding, retrieval, queue, cache, or additional infrastructure packages are used.

## 5. Database Design

### `users`

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key, generated by PostgreSQL |
| `display_name` | TEXT | Required and non-empty |
| `email` | TEXT | Required, unique |
| `role` | TEXT | Checked against the defined project role set |
| `created_at` | TIMESTAMPTZ | Database timestamp |

### `projects`

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key, generated by PostgreSQL |
| `name` | VARCHAR(160) | Required and non-empty |
| `description` | TEXT | Required, defaults to empty |
| `selected_domain` | VARCHAR(120) | Defaults to `Trade Finance / Letter of Credit`; remains data-driven |
| `status` | TEXT | Checked values: `DRAFT`, `ACTIVE`, `ARCHIVED` |
| `owner_id` | UUID | Nullable FK to `users`; becomes null if the owner is deleted |
| `created_at`, `updated_at` | TIMESTAMPTZ | Database timestamps |

Indexes support owner and recent-update lookup. The schema uses idempotent `CREATE TABLE/INDEX IF NOT EXISTS` statements and seeds one local development owner plus the initial LC project using stable IDs. Re-running initialization preserves records.

## 6. API Structure

| Method | Route | Behavior |
|---|---|---|
| GET | `/api/health` | Returns API status JSON |
| GET | `/api/health/db` | Executes a database connectivity query; reports unavailable as HTTP 503 |
| GET | `/api/projects` | Lists database projects with owner display name |
| GET | `/api/projects/:id` | Returns one project, HTTP 404 when missing and HTTP 400 for malformed UUID |
| POST | `/api/projects` | Validates and persists project fields, then returns the created record |
| GET | `/api/users` | Lists user/role foundation rows |
| POST | `/api/users` | Validates and creates a user/role foundation row |

Responses use `{ "data": ... }` for successful resource operations and `{ "error": { "message", "code" } }` for errors. Queries use parameters. Server stack traces are not returned to API consumers.

## 7. Frontend Structure

- Overview dashboard with API status, project counts, recent database-backed projects, and a link to the project list.
- Projects page with creation form and cards populated from `GET /api/projects`.
- Project detail route loads the record from `GET /api/projects/:id`.
- Project creation posts through `POST /api/projects`, updates the UI from the returned server resource, and navigates to its detail page.
- Reusable project card, status pill, project form, and API client components.
- Request failures and empty/loading states are shown to the user.
- The UI identifies the selected Trade Finance / Letter of Credit context and makes clear that AI analysis is deferred.

## 8. Environment Configuration

Root `.env.example` documents Compose and API values; `frontend/.env.example` documents the browser API URL. Compose reads `POSTGRES_*`; the API reads `DATABASE_*` and `API_PORT` / `FRONTEND_ORIGIN`; Vite reads `frontend/.env.local`. The operator copies each example to its local environment file, replaces the sample password, and keeps the Compose and API database credentials consistent. Local environment files are ignored. No secrets are embedded in source files.

## 9. Docker Setup

`docker-compose.yml` contains one `postgres` service, PostgreSQL 16 Alpine, a named `postgres_data` volume, configurable port and credentials, and a `pg_isready` health check. No other services are added. PostgreSQL is expected to be run locally through Docker; a host PostgreSQL installation is not required.

- `GET /api/projects/c8358f87-323e-4b3c-8f6f-fabf143179eb` retrieved the created project. After restarting the backend, the same GET still retrieved it, verifying database persistence.

## 11. Limitations

- User rows and roles are a data foundation only; no authentication, session management, MFA, or authorization is implemented.
- No project update/delete, advanced project management, or collaboration workflows.
- Database integration checks require a running Docker PostgreSQL service.
- Local sample owner and initial project are development bootstrap records, not real users or business data.
- No specific regulations, jurisdiction, bank procedures, or compliance interpretation are encoded.

## 12. Explicitly Deferred Functionality

No LLM integration, agent orchestration, RAG, embeddings, knowledge ingestion, requirements extraction/classification/quality analysis, clarification engine, compliance/security/privacy/risk analysis, automated artefact generation, traceability engine, SDLC selection/workflow generation, prompt-injection detection, advanced audit, MFA, production authentication, or production deployment is implemented. These remain for later phases, consistent with the Phase 1 scope and boundary.
